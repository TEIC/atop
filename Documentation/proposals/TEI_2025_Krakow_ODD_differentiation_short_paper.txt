The original plan for the TEI/ODD system was for two types of user-facing ODD files:¹ base ODDs which contain specifications for classes, elements, etc., likely arranged within modules; and customization ODDs which assert which specifications from the associated base ODD should be used to create a particular markup language. These two types were to be differentiated by the presence of a <schemaSpec> element in the latter, and not in the former. But two realities impinge on that plan:
1. Many users of the TEI/ODD system have created stand-alone markup languages using a single ODD that has a <schemaSpec> element. Such an ODD is not a customization ODD, but nonetheless has a <schemaSpec>.
2. Using the current Stylesheets the “compiled” ODD (the initial output of combining a customization ODD with a base ODD) contains a <schemaSpec> element. This compiled ODD may be used to generate a customized schema, but also may be used as the base for another customization, in which case it is not a customization ODD, but nonetheless has a <schemaSpec>.
Thus we cannot use the mere presence of a <schemaSpec> to automatically differentiate between these two types of ODDs, which we need to be able to do to effect automatic ODD chaining. Our paper will discuss these issues, demonstrate a moderately complicated XPath that we think would do the job,² and suggest a simple modification to the TEI scheme that would solve the problem: Requring the @source attribute of <schemaSpec>, and providing a special-purpose value (e.g. "tei:NONE") for use when the ODD is a base ODD.

Notes
¹ There are also intermediate ODDs (called “compiled” or “processed”) that the typical user of the system would probably never see, and certainly would not have to read.
² if (//schemaSpec[moduleRef|elementRef|classRef|dataRef|macroRef]) then "customization" else "base"
